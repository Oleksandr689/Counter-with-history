# Практична робота 6.1 · Базовий State Management

**Дисципліна:** Програмування для мобільних платформ  
**Варіант 1:** Лічильник з історією  
**Технології:** Flutter SDK, Dart, Material 3. Сторонніх пакетів керування станом немає.

## Мета

Розділити локальний стан екрана і спільний стан застосунку. Порівняти передавання
даних через конструктори та колбеки з доступом через ChangeNotifier і InheritedNotifier.
Обмежити перебудови інтерфейсу віджетами, які показують змінені дані.

## Що реалізовано

- Додавання, віднімання та скидання лічильника.
- Крок 1, 5 або 10; він зберігається локально через setState.
- Заборона від’ємних значень із поясненням у SnackBar.
- Незмінний HistoryEntry: час, дія, значення до та після; конструктор const.
- Окремий екран історії, новіші записи зверху, ListView.builder.
- Очищення історії без зміни поточного значення.
- Бейдж кількості записів в AppBar кожного екрана.
- Два етапи реалізації, теги Git, автоматизовані тести та workflow GitHub Actions.

Скидання вже нульового значення та відхилена спроба віднімання не створюють запис:
історія фіксує тільки фактичні зміни. Дані зберігаються в оперативній пам’яті;
після повного перезапуску застосунку вони очищуються. Вибір іншої вкладки зберігає
значення й історію, але повторне відкриття лічильника починає локальний крок із 1.

## Стан перевірки

Код підготовлено та переглянуто, але **flutter analyze, flutter test і збірку не
підтверджено запуском**: автоматична перевірка середовища заблокувала запуск Flutter
через можливий доступ до службового endpoint метаданих. Журнал виконання та
скриншоти застосунку не підмінено вигаданими результатами. Нижче наведено команди,
сценарії та очікувані результати для перевірки на власному комп’ютері.

До здачі потрібно виконати перевірки, додати реальні скриншоти й фактичний журнал,
опублікувати репозиторій. Workflow також ще не виконувався на GitHub.

## Два етапи в Git

```bash
git switch --detach stage-1-lifting
flutter pub get
flutter run
```

На етапі 1 LiftedCounterHost володіє значенням і списком історії. setState змінює
спільний стан; CounterScreen та HistoryScreen отримують дані конструкторами й
повертають дії через колбеки. Це демонструє підняття стану до спільного предка.

```bash
git switch --detach stage-2-inherited
flutter pub get
flutter run
git switch main
```

На етапі 2 CounterApp створює CounterModel і звільняє її у dispose(). CounterScope
надає модель піддереву. CounterScope.of(context) створює залежність від повідомлень
моделі, а CounterScope.read(context) використовується лише в обробниках команд і
не підписує весь екран на перебудову. Через проміжні віджети спільний стан не передається.

## Таблиця стану

| Дані | Вид стану | Етап 1 | Етап 2 | Чому саме там |
|---|---|---|---|---|
| Значення лічильника | Стан застосунку | LiftedCounterHost | CounterModel | Пов’язане зі спільною історією |
| Список змін | Стан застосунку | LiftedCounterHost | CounterModel | Потрібний обом екранам та бейджам |
| Крок 1/5/10 | Ефемерний | CounterScreen, setState | CounterScreen, setState | Потрібний лише для взаємодії з лічильником |
| Поточна вкладка | Ефемерний | LiftedCounterHost | CounterHost, setState | Навігаційний стан інтерфейсу |
| Кількість записів | Обчислюване значення | history.length | model.history.length | Немає потреби дублювати список окремим числом |

Контролерів введення, таймерів і StreamSubscription тут немає. Власник моделі
викликає `_model.dispose()`; InheritedNotifier керує своєю підпискою на notifier.

## Структура lib

- `main.dart` — запуск, тема, створення та звільнення моделі.
- `models/history_entry.dart` — незмінний запис історії.
- `state/counter_model.dart` — правила зміни значення, історія, notifyListeners.
- `state/counter_scope.dart` — InheritedNotifier, of та read.
- `screens/counter_host.dart` — перемикання екранів.
- `screens/counter_screen.dart` — кнопки та локальний крок.
- `screens/history_screen.dart` — екран історії та команда очищення.
- `widgets/counter_value.dart` — відображення значення.
- `widgets/history_badge.dart` — кількість записів.
- `widgets/history_list.dart` — підписка списку на модель.
- `widgets/history_tile.dart` — відображення одного запису.

## Перебудови

У ключових build є debugPrint. Після початкового запуску очистіть консоль і
натисніть «+». **Очікуваний фрагмент, ще не фактичний журнал:**

```text
build: HistoryBadge
build: CounterValue
```

Порядок рядків не принциповий. CounterScreen, CounterHost і CounterApp не читають
модель через of(context), тому зміна лічильника не повинна викликати їх build.
Тест `test/rebuild_test.dart` перевіряє саме набір двох перебудованих віджетів.
На екрані історії після очищення очікуються HistoryBadge та HistoryList.

InheritedNotifier повідомляє **всі залежні від нього віджети**, а не вибирає окремі
поля моделі. Точкові перебудови забезпечені розташуванням залежностей у малих
віджетах. Неактивний екран вилучений із дерева. Зміна кроку викликає локальний
setState і закономірно перебудовує CounterScreen.

Місце для фактичного журналу та інструкція: [docs/rebuilds.md](docs/rebuilds.md).

## Перевірка сценаріїв

| Дія | Очікуваний результат |
|---|---|
| Початковий запуск | Значення 0, бейдж 0, крок 1 |
| «+», крок 1 | Значення 1, запис 0 → 1 |
| Обрати 5 та натиснути «+» | Додано 5, історія зростає на один запис |
| Відняти 10 від 5 | Значення залишається 5, SnackBar, без нового запису |
| «Скинути» після 15 | Значення 0, запис 15 → 0 |
| «Скинути» при 0 | Без зміни історії |
| Відкрити історію | Записи у зворотному хронологічному порядку |
| Очистити історію | Порожній стан, бейдж 0, значення збережене |
| Повернутися на лічильник | Спільне значення збережене, локальний крок 1 |

`test/app_test.dart`: кнопки, кроки, нижня межа, навігація й очищення.
`test/model_test.dart`: незмінний список, порядок записів, відсутність зайвих сповіщень.
`test/rebuild_test.dart`: точність перебудов та демонтаж кореневого віджета.
Тести додано, але успішне проходження ще потрібно підтвердити.

## Висновок

Підготовлено дві реалізації одного інтерфейсу. На першому етапі спільні дані
піднято до предка, на другому — відокремлено в модель із сповіщеннями. Крок
залишено локальним. Залежності від моделі розміщено у віджетах значення, бейджа
та історії. Остаточне підтвердження працездатності потребує виконання наведених
перевірок у Flutter-середовищі.
